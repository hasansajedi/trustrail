# OWASP LLM Top 10:2025 mapping

This table summarizes trustrail coverage against the OWASP Top 10 for LLM
Applications 2025. It is an engineering aid, not evidence of compliance or
complete mitigation.

| OWASP LLM risk | trustrail rules and APIs | Additional controls required |
| --- | --- | --- |
| **LLM01:2025 Prompt Injection** | PI-001 through PI-017 cover direct/indirect override, jailbreak, metadata poisoning, token smuggling, tool responses, encoding, multilingual attacks, payload splitting, adversarial suffixes, extracted multimodal content, invisible Unicode channels, and cross-boundary assembly; RAG-004 preserves provenance; MEM-001 protects persistent writes | Pattern detection cannot cover every semantic attack. Require least privilege, application-assigned trust, deterministic tool authorization, trusted extraction, egress controls, approval boundaries, and application-specific red teaming |
| **LLM02:2025 Sensitive Information Disclosure** | SD-001 through SD-016 detect PII, financial data, credentials, provider API tokens, and high-entropy secrets; SD-017 compares output with caller-supplied `ProtectedData`; `SensitiveDataMode` provides default, redact, block, and explicit allow policies; `DataLifecycleManager` restricts purpose, residency, retention, training, and export across derived copies; findings, audit events, and integration error logs are content-free | Retrieval authorization, tenant isolation, data minimization, authoritative consent and legal policy, provider-side DLP, credential rotation, durable lifecycle state, and privacy-preserving model/training controls |
| **LLM03:2025 Supply Chain** | `ArtifactManifest` inventories models, datasets, prompts, adapters, plugins, packages, services, licenses, provenance, immutable revisions, approval state, and lifecycle status; `ArtifactVerifier` checks exact metadata and SHA-256/384/512 digests, blocks unknown or changed artifacts, and can pin the manifest fingerprint out of band; SC-001 scans third-party responses and is enabled at tool/external boundaries; RAG envelopes protect retrieved provenance | Signed attestations and BOMs, vulnerability and license scanning, independent supplier review, model/data evaluation, patch and revocation processes, and trusted hardware/device attestation where applicable |
| **LLM04:2025 Data and Model Poisoning** | `DataIngestionRecord` and `DataPoisoningVerifier` bind training, fine-tuning, RAG, memory, metadata, and model content to source policy, writer/tenant/purpose authorization, immutable versions, integrity digests, transformation lineage, anomaly scores, and content-free quarantine findings; custom detectors fail closed; DP-001, PI-007, RAG provenance rules, and MEM-001 add runtime RAG, nested-metadata, and persistent-memory controls | Authenticated control-plane identity, dataset/version governance, independent labels and evaluation sets, statistical drift and bias monitoring, red-team/backdoor testing, tenant-isolated indexes, restricted model deserialization, quarantine/rebuild/rollback operations, and human review |
| **LLM05:2025 Improper Output Handling** | OS-001 through OS-013 detect HTML, paths, shell syntax, URLs, Markdown images, dangerous code, SQL, templates, logs, LDAP, XML/XPath, and file-wrapper injection; `SafeOutputHandler` provides typed destination contracts for HTML/JavaScript encoding, Markdown/URL validation, rooted paths, strict JSON, prepared-statement data, fixed argv, and non-executing tool plans | CSP and final HTML sanitization, prepared statements, fixed templates and executables, DNS/redirect/egress controls, secure filesystem APIs, deterministic authorization, scoped credentials, approval, and sandboxing remain application responsibilities |
| **LLM06:2025 Excessive Agency** | `ToolCapability`, `ToolAuthorizationPolicy`, and `ToolAuthorizer` provide complete mediation for exact tool/version identity, closed scalar argument contracts, authenticated principal and tenant, short-lived intent, authoritative resource ownership, scope non-expansion, bound single-use approval, and call/chain/retry/parallel/autonomy budgets; EA-001 through EA-005, AG-001 through AG-003, and TL-001 through TL-004 add heuristic and session defense-in-depth | End-user downstream credentials and service-side authorization, shared atomic budget/replay state for distributed deployments, network egress and transaction/value limits, tool sandboxing and implementation security, durable content-free audit, idempotency, rollback, and independent human review remain required |
| **LLM07:2025 System Prompt Leakage** | `SystemPromptValidator` provides typed, classified construction and rejects sensitive data and prompt-based authorization; MT-002 detects direct, partial, reconstruction, encoded, indirect, and cross-boundary extraction requests; `SystemPromptLeakageDetector` blocks structured, normalized verbatim, partial, and Base64-encoded prompt disclosure with content-free results | Prompts are not secrets or security controls. Keep credentials and authorization outside prompts; enforce provider retention, access control, tenant isolation, egress policy, monitoring, rotation, and application-specific multi-turn red teaming |
| **LLM08:2025 Vector and Embedding Weaknesses** | `VectorChunk`, `VectorEmbedding`, and `VectorIndexEntry` preserve integrity-linked source, trust, access, embedding-model, index, and namespace lineage; `SecureVectorWorkflow` completely mediates tenant, user, scope, document, and resource access, recomputes cosine similarity, rejects rank and normalized-duplicate manipulation, and scans authorized hits before labeled context assembly; `DataLifecycleRecord` carries use and deletion obligations through documents, chunks, embeddings, caches, logs, and memory; RAG-001 through RAG-004 add provenance and instruction defenses | Physical vector-store partitioning, encryption, service-side access control, protected/signed and durable catalogs, embedding-inversion risk reduction, provider-specific score validation, corpus-wide anomaly monitoring, independently verified replica/backup deletion, immutable audit, behavior evaluation, citation validation, and human review remain required |
| **LLM09:2025 Misinformation** | GR-001 through GR-005 warn on hallucination indicators, absolute claims, citation-shaped output, unreviewed high-risk advice, and sycophancy; `GroundingEvidence`, `GroundingClaim`, `EvidenceRelation`, and `GroundingCitation` preserve exact provenance and confidence; `EvidenceGroundingVerifier` blocks unsupported, contradicted, untrusted, tampered, misclassified, or uncertainty-hiding output and requires a digest-bound human decision for high-impact claims | Source authentication and freshness, independent semantic assessment, confidence calibration, diverse domain evaluations, qualified reviewers, decision appeals, behavior monitoring, and application-specific claim extraction remain required; hashes and citations do not prove truth |
| **LLM10:2025 Unbounded Consumption** | RL-001 through RL-009 provide text-stage limits and amplification detection; `ResourceBudgetManager` atomically reserves authenticated principal/tenant concurrency and request windows, exact input/requested-output tokens, retries, tool loops, session duration and cumulative tokens, then validates actual output; `BoundedDecompressor` caps gzip/zlib input, output, and expansion ratio and rejects malformed or concatenated streams; results expose content-free audit counters | A shared atomic gateway for multi-process/global quotas, authoritative provider usage and monetary budgets, exact multimodal token accounting, infrastructure CPU/memory/network controls, early streaming upload limits, parser/codec/archive sandboxes, provider-side deadlines and cancellation, Sybil resistance, and long-term model-extraction behavior monitoring remain required |

Coverage depends on the selected `GuardStage`, configuration, custom rules, and
application enforcement. Review the [threat model](security/threat-model.md) and
test against threats specific to your system.

## OWASP AI Testing Guide v1 release gates

| Testing Guide layer | Campaign coverage | Additional controls required |
| --- | --- | --- |
| **AI Application Testing** | `AITestLayer.APPLICATION` versions application attacks and controls, runs repetitions with bounded budgets, and gates explicit point-estimate or confidence-aware thresholds | Application-specific assertions, representative user journeys, authenticated test environments, and manual exploratory testing |
| **AI Model Testing** | `AITestLayer.MODEL` binds evidence to provider, model revision, configuration digest, optional deterministic seeds, and per-case outcomes | Provider/version-specific behavioral, robustness, bias, privacy, and safety tests; seed support does not make model revisions equivalent |
| **AI Infrastructure Testing** | `AITestLayer.INFRASTRUCTURE` records deployment revision and supports isolation, egress, resource, and deployment-control probes through an application adapter | Hardened external probes, infrastructure attestations, authorization, network enforcement, and environment isolation |
| **AI Data Testing** | `AITestLayer.DATA` records corpus and data revisions and supports poisoning, provenance, privacy, and retrieval-integrity assertions | Protected representative datasets, lawful handling, independent provenance, drift analysis, and corpus governance |
| **Repeatability and release comparison** | `AITestCampaignRunner` records configuration/corpus digests, repetitions, Wilson confidence intervals, error/attack budgets, stable IDs, limitations, and payload-free integrity-bound evidence; authenticated baselines block statistical or critical security regressions | Protected or signed baseline approval, CI artifact retention, key management, review of threshold changes, and continued red teaming |

This implements evaluation orchestration aligned with the
[OWASP AI Testing Guide](https://owasp.org/www-project-ai-testing-guide/); it does
not claim that the example corpus implements every OWASP test or that a passing
run is certification. See [AI trustworthiness release gates](guides/ai-testing-release-gates.md)
for configuration, assumptions, and residual risks.

## OWASP GenAI data security and AISVS lifecycle controls

| Data-security objective | trustrail controls | Additional controls required |
| --- | --- | --- |
| **Inventory and classify GenAI data** | `DataLifecycleMetadata`, `DataStorageLocation`, and `DataLifecycleRecord` inventory typed prompts, outputs, retrieved documents, chunks, embeddings, caches, traces, logs, memory, datasets, and model artifacts with integrity-bound classification, purpose, residency, retention, consent, legal holds, subjects, content digest, locations, and versions | Authoritative discovery and classification, data-flow mapping, legal-basis decisions, asset ownership, storage access control, encryption, and protected durable metadata |
| **Preserve provenance and restrictions** | `require_derivation()` binds exact source record versions and blocks classification, purpose, residency, retention, consent, legal-hold, or subject-lineage downgrade across single- and multi-source derivations | Complete mediation of every ingestion, transformation, model, RAG, cache, observability, memory, export, and training path; authenticated transformers and metadata issuers |
| **Limit use, destination, retention, and training** | `require_use()` checks tenant, exact record version, active state, purpose, destination residency, retention deadline/extension, training consent, and classification policy before content access | Service-side authorization, provider contracts and settings, regional routing evidence, consent and purpose governance, DLP, monitoring, and downstream enforcement |
| **Delete copies and derivatives** | `plan_deletion()` resolves artifact or one-way subject references through transitive lineage and every declared location; short-lived plans preserve legal holds and bind exact record versions; `execute_deletion()` tombstones before delete and validates action-bound receipts and independent verification | Shared atomic durable workflow state, authenticated connectors, retry and reconciliation, replicas/cache/index/snapshot/backup coverage, downstream-processor coordination, cryptographic-key lifecycle, regulatory evidence, and model unlearning or retraining where required |

and [OWASP AISVS](https://github.com/OWASP/AISVS) training-data traceability and

compliance evidence. See
[GenAI data lifecycle and verified deletion](security/data-lifecycle.md) for the

## OWASP AISVS C1 training-data integrity and traceability

| AISVS C1 objective | trustrail controls | Additional controls required |
| --- | --- | --- |
| **C1.1.1 Feature minimization** | `DatasetFeaturePolicy` approves only purpose-required feature IDs and binds personal/sensitive features to exclusion, redaction, anonymization, or encryption; `TrainingDatasetManifest` declares the effective feature set and intended purpose | Authoritative data discovery/classification, necessity review, lawful basis, minimization within feature values, and downstream enforcement in training code |
| **C1.1.2–C1.1.4 Inventory and integrity** | Existing provenance and lifecycle records inventory source/purpose/history; `TrainingDatasetManifest` binds an immutable dataset version, source/output digests, and an integrity-linked chain of approved transformation versions and actors | Authenticated storage/transport, durable inventory, license/collection governance, signed attestations, protected policy state, and continuous integrity monitoring |
| **C1.2.1 Annotation access control** | `TrainingDatasetPolicy` allowlists label writers and approvers; the verifier requires approval, can prohibit self-approval, and excludes identities and raw labels from findings/evidence | Labeling-platform authentication, least privilege, session security, revocation, separation of duties, and durable audit logs |
| **C1.2.2 Label integrity** | Each `TrainingAnnotation` binds canonical label bytes to a digest; `approved_annotation_set_digest` separately pins ordered label hashes, sample references, origin, writer, approver, confidence, and handling in trusted policy | Protected signing keys/policy store, authenticated contributors, immutable object storage, backup integrity, and incident response |
| **C1.2.3 Sensitive labels** | Dataset features and labels declare sensitivity-aware handling; unsafe plain or unapproved handling is quarantined, while content-free results omit label values | Actual encryption/redaction/anonymization enforcement, key management, access monitoring, re-identification testing, retention/deletion, and privacy review |
| **C1.3.1 and C1.3.4 Poisoning/disallowed content** | `DataPoisoningVerifier` scans provenance, authorization, anomaly signals, content, and nested metadata before governed labeling admission | Domain-specific content classifiers, statistical poisoning analysis, sandboxed inspection, human review, and independent clean data |
| **C1.3.2 Automated-label quality** | Automated/synthetic labels require confidence; application hooks return bounded consistency and clean-label scores and fail closed on absence/errors | Calibrated confidence, representative held-out labels, multiple independent reviewers/models, drift monitoring, and adjudication |
| **C1.3.3 Bias evaluation** | `BiasEvaluationRequest` accepts provider-neutral aggregate group metrics; per-metric sample, absolute-gap, and parity-ratio thresholds produce content-safe `BiasEvidenceReport` records | Domain- and jurisdiction-appropriate fairness definitions, intersectional analysis, privacy controls, qualified review, remediation, and production outcome monitoring |
| **C1.3.5 Clean-label poisoning** | Quality hooks gate normalized clean-label risk scores and preserve only evaluator IDs and evidence digests in results | Adversarial/domain-specific detectors, influence/outlier analysis, contributor reputation, retraining tests, and ongoing backdoor-trigger evaluation |
| **Governed exceptions** | `BiasExceptionGrant` binds a justification and approval digest to one evaluation/metric/group and is honored only while unexpired and authenticated by an external verifier | Non-spoofable approval UX, signed grants, revocation/shared replay state, monitoring, appeals, and periodic reassessment |

See [training-data labeling integrity and bias evaluation](security/training-data-governance.md)
for configuration and residual risks. This is an engineering mapping to
[OWASP AISVS C1](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C01-Training-Data-Integrity-and-Traceability.md),
not certification or a claim that a dataset or model is unbiased.

| OWASP agentic risk | trustrail APIs | Additional controls required |
| --- | --- | --- |
| **ASI01:2026 Agent Goal Hijack** | `GoalManifest` integrity-binds the authorized objective, constraints, owner/tenant, primary actor, permitted actions/delegates, approval context, session, execution, expiry, revision, parent, and original goal digest; `GoalIntegrityGuard` completely mediates ordered plan steps and delegation, rejects stale/cross-session bindings, detects direct/encoded/split drift, approval-gates every material mutation, prevents approval replay, bounds cumulative work, and emits content-free audit evidence | Trusted manifest issuance and identity, complete mediation of every planner/scheduler/delegate/resume path, protected or signed manifest/state storage, atomic distributed execution state, narrow capabilities plus downstream `ToolAuthorizer`, semantic and multilingual plan review, behavioral monitoring, secure human approval UX, red-team evaluation, sandboxing, service-side authorization, and egress/transaction limits remain required |

| **ASI03:2026 Identity and Privilege Abuse** | `AgentIdentity`, `DelegatedCapability`, and `DelegationChain` preserve immutable human/service/agent/sub-agent lineage while narrowing tenant, scopes, audience, purpose, lifetime, and depth; `DelegatedIdentityAuthorizer` authenticates every capability, binds the presenter, checks ancestor revocation, prevents forwarding and amplification, and requires request-bound single-use step-up/JIT grants for configured high-impact scopes | Trusted workload and user authentication, signed or protected capability issuance, proof of possession, secure token exchange, shared atomic revocation/replay state, downstream service authorization, complete mediation, short authorization TTLs, secure approval UX, tenant/resource checks, monitoring, and incident response remain required |

| **ASI07:2026 Insecure Inter-Agent Communication** | `InterAgentMessageEnvelope` and `InterAgentMessageSigner` use Ed25519 to bind the sender, recipients, tenant, session, authorized goal, task, purpose, scope, current delegation-chain digest, type, payload digest, nonce, sequence, expiry, and individually signed transformation lineage; `InterAgentMessageVerifier` pins agent keys, re-authorizes every recipient against current delegated capability and revocation state, enforces explicit routes and bounded fan-out, rejects unsigned/tampered/expired/replayed/out-of-order/cross-context messages, and emits content-free evidence | Authenticated key provisioning and rotation, protected private keys, mutually authenticated and confidential transport, a shared atomic replay/order store across workers and regions, clock synchronization, complete mediation, durable audit, rate limiting, downstream authorization, semantic payload validation, monitoring, and incident response remain required |
| **ASI08:2026 Cascading Failures** | `FailureContainmentPolicy` declares dependency health, criticality, tenant-scoped failure domains, independent integrity-pinned fallbacks, retry/recursion/cost/tool-call limits, and rolling error/latency/cost/anomaly thresholds; `FailureContainmentManager` atomically issues single-use permits, isolates breaker state by tenant, limits half-open probes, authenticates outcome reports, prevents fallback substitution and duplicate side effects, and emits deterministic degraded-mode, cancellation, compensation, and recovery events | Shared atomic state is required across workers and regions; trusted health, identity, anomaly, cost, and signed report sources; downstream idempotency and transactions; infrastructure timeouts and cancellation; capacity isolation, bulkheads, load shedding, chaos testing, monitoring, incident response, and disaster recovery remain required; compensation cannot undo irreversible effects and a fallback still needs independent safety and authorization checks |
